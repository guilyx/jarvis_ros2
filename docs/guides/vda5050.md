# Jarvis for VDA 5050 fleet managers

A fleet manager that drives robots over [VDA 5050](https://github.com/VDA5050/VDA5050) reads each
robot's state, and in it the robot's `errors`: what stops it from taking orders, what needs a person.
The gateway serves Jarvis's open faults as VDA 5050 error objects, so the robot's VDA 5050 adapter
reports them too, with a level the fleet manager acts on and a hint from the fault's runbook.

1. [Merge Jarvis's errors into your state](#1-merge-jarviss-errors-into-your-state)
2. [How faults become errors](#2-how-faults-become-errors)
3. [Map your codes](#3-map-your-codes)

## 1. Merge Jarvis's errors into your state

The robot's adapter owns its state message (`uagv/v3/<manufacturer>/<serialNumber>/state`): Jarvis
doesn't publish a second one. Each time the adapter builds the state, it adds Jarvis's errors to its
own:

```python
import requests  # or any HTTP client; the gateway is on the robot

JARVIS = "http://127.0.0.1:8080/api/v1/vda5050/errors"


def jarvis_errors():
    try:
        return requests.get(JARVIS, timeout=0.5).json()["errors"]
    except (requests.RequestException, KeyError, ValueError):
        return []  # Jarvis down: report your own errors, don't stop reporting


state["errors"] = own_errors + jarvis_errors()
```

```bash
curl -s localhost:8080/api/v1/vda5050/errors
# {"version": "3.0", "errors": [{"errorType": "ros.topic.stale", "errorLevel": "URGENT",
#   "errorReferences": [{"referenceKey": "component", "referenceValue": "lidar"}, ...],
#   "errorDescription": "/scan: no message for 1.0 s",
#   "errorHint": "A managed driver: restart it. ros2 jarvis recover restart-lifecycle-node ..."}]}
```

Reading needs a viewer: the anonymous role (a viewer by default) on the robot, or a token
(`Authorization: Bearer ...`) if you turned anonymous access off ([security guide](security.md)).

## 2. How faults become errors

One error per open root cause (`ACTIVE` or `LATCHED`). Muted symptoms are left out, so the fleet
manager sees the cause (the lidar) rather than everything it broke (the costmaps). Pending faults
aren't errors yet.

| VDA 5050 | From |
|----------|------|
| `errorType` | The Jarvis code (`sensor.scan.stale`), or the type you map it to (§3). VDA 5050 types are an extensible enumeration |
| `errorLevel` (3.0) | WARN and below: `WARNING`; ERROR: `URGENT`; CRITICAL: `CRITICAL`; CRITICAL and latched (a person must clear it): `FATAL` |
| `errorLevel` (2.x) | `WARNING`, or `FATAL` for what would be `CRITICAL` or `FATAL` in 3.0 |
| `errorReferences` | `component`, `faultId`, `incidentId`, and `jarvisCode` when the type is mapped |
| `errorDescription` | The fault's message |
| `errorHint` (2.1 and later) | The first step of the "Fix" section of its runbook |

Most severe first. The levels follow VDA 5050's meaning: at `CRITICAL` the robot shouldn't continue
its order, at `FATAL` it can't take new ones. Jarvis tells the fleet manager; the robot's own safety
and its adapter decide what the robot does.

## 3. Map your codes

In `gateway.yaml`, the VDA 5050 version your fleet manager speaks, and for the codes it should know by
a predefined type, or at another level:

```yaml
schema: jarvis.gateway/v1
vda5050:
  version: "3.0"                     # "2.1" or "2.0" for older fleet managers
  errors:                            # first match by code (glob)
    - { code: nav.localization.*, type: LOCALIZATION_ERROR, level: FATAL }
    - { code: ros.action.navigate_to_pose.aborted, type: NODE_UNREACHABLE, level: CRITICAL }
    - { code: "medkit.*", level: URGENT }
```

The e-stop itself goes in the state's `safetyState.eStop`, as VDA 5050 says; Jarvis's fault adds what
it did to the robot.

A mapped type keeps the Jarvis code in the references (`jarvisCode`), so the fault, its incident and
its runbook stay one click away in the dashboard.
